# Imagen 최적화 결과와 실험 이력

2026-10-28 기준. 다음 최적화 작업에서 중복 실험을 피하기 위한 기록이다. 구현과 조건이 바뀌면 과거 측정은 재검증해야 한다.

## 현재 상태

- 목표는 **같은 16스텝 편집 조건과 출력을 유지하면서 디노이징 50초 이하**다. 아직 달성하지 못했고, 추가 최적화는 일시 중지했다.
- 같은 512×352 편집 입력, M3 Pro 36GB, FLUX.3 Klein Q8, MLX 0.32.4, 시드 7에서 변경 전 72.81초, 적용 후 64.60초였다. 각 1회이고 연속 쌍이 아니므로 반복 가능한 개선 폭을 확정할 수 없다. 로딩·인코딩·디코딩·저장 제외, 첫 가중치 준비 포함이다.
- 적용 후 최종 잠재값은 해당 Python 기준과 비트 일치했다. 같은 사진의 시드 19도 64.49초로 해당 기준과 비트 일치했고, 별도의 실제 생성 경로에서 65.92초 및 기준과 RGB 픽셀 일치를 확인했다. 사진·프롬프트·시드·Mac 전체에 대한 보증은 아니다.
- **C++ 전환만으로 속도가 보장되지 않는다.** 기존 Python과 C++ 모두 대부분의 행렬곱을 MLX 네이티브/Metal에서 실행한다. 16스텝 과거 비교는 Python 75.07초, C++ 75.38초였으며 잠재값은 비트 일치했다.

## 최종 적용된 최적화

| 영역 | 적용 내용 | 주의 |
|---|---|---|
| 실행 구조 | Python에서 입력 인코딩·출력 디코딩, C++/MLX에서 transformer 및 스케줄러 수행 | 실제 전체 작업 시간은 디노이징 시간보다 길다 |
| 가중치 | 큰 블록의 Q8을 BF16으로 1회 복원, Q/K/V 결합, eval 전에 불필요한 Q8 참조 해제 | 4스텝 MLX 피크 14.40→12.39GB 사례; 총 시스템 메모리는 아님 |
| 행렬곱 | 큰 MLP 입력 투영의 출력 채널 약 45%는 CPU FP32, 나머지는 GPU BF16 | 1,024토큰 기준. 이 비율의 최적성은 하드웨어와 형상에 의존 |
| 커널 | Q/K 정규화·RoPE·V 배치, modulation, SwiGLU, 잔차 융합 | 원본의 자료형과 중간 반올림 유지 |
| 요청 내 고정값 | 텍스트·참조 입력 투영, 위치 ID의 RoPE 준비 | target timestep에 의존하는 초기 블록 결과는 고정값이 아님 |
| 마지막 joint 블록 | 최종 결과에 필요한 이미지 토큰만 query 결과와 MLP/출력 계산. K/V는 전체 토큰 유지 | 최종 QKV 투영 자체는 아직 전체 토큰에 대해 수행 |
| 실행 중첩 | 각 큰 블록의 attention 출력과 MLP 입력을 `async_eval`로 함께 제출 | 앞뒤 단일 측정 72.81→64.60초, 정확한 효과의 반복 통계는 없음 |

원본 Python 실행기의 역사적 결과는 [실행기 최적화](optimization.md)와 [벤치마크](benchmarks.md)에 있다. 실제 코드와 실행 경로는 [구조](architecture.md), [개발](development.md)을 참조한다.

## 시도하고 기본 경로에 적용하지 않은 방법

다음의 시간은 각 단일 실험, 장치·입력·시점이 다를 수 있다. 다른 행의 숫자를 하나의 엄격한 A/B 비교로 묶지 않는다. 4스텝은 주로 후보 선별용이고 16스텝 결과를 보증하지 않는다.

| 범주 | 실험 및 관찰 | 판단 |
|---|---|---|
| 스텝과 잔차 재사용 | 16 업데이트 중 joint 블록을 6회 재사용: 52.60초, RGB PSNR 45.34 dB. 7회 재사용: 45.96초, 31.60 dB. 선형 외삽도 46.27초, 31.41 dB | 출력과 이미지가 달라지고 사용자가 디테일 손실을 확인하여 제외. PSNR만으로 품질을 보장할 수 없음 |
| early stream 재사용 | target timestep에 의존. 두 스텝을 배치한 4스텝 실험 20.84초, 잠재 RMSE 0.0817; 개별 선계산 18.35초 | 배치는 수치 불일치, 선계산은 빠르지 않아 제외 |
| 정확한 토큰 캐시 | 실제 16스텝 인접 입력에서 이미지 704개, 초기 참조 특징 1320개 중 벡터 전체가 BF16으로 같은 토큰 0개 | 이 입력에서 완전 동일 토큰 재사용의 이점 없음 |
| 정확한 0 생략 | 16스텝 modulation gate 및 1개 블록 SiLU 출력에 정확한 0 없음. 표본 입력 0.08%, 가중치 0.05%만 0 | 표본에서 유의미한 희소성 없음 |
| C++ 그래프 컴파일 | 직접 16스텝 71.87초였으나 실제 생성 경로는 컴파일 75.91초, 직접 74.28초; 33개 블록 그래프 공유도 이점 불명 | 반복 가능한 가속이 없어 자동 적용 철회 |
| 시간·스케줄 캐시 | zero timestep 캐시, delta 일괄 계산, `dt.eval` 제거 | 동일 출력 사례는 있으나 뚜렷한 이득 없음 |
| CPU 분할 비율 | 30/40/42/45/47/55%, 조건 스트림 별도 분할 등 | 45%가 여러 실험에서 유리했으나 단일 측정 변동이 큼. 다른 형상·기기는 별도 측정 필요 |
| CPU/GPU 재분배 | QKV·attention 출력·MLP 출력에도 CPU 할당, QKV CPU 60%, 토큰 축 45% 분할 | 더 느림. 토큰 축 분할은 정확하지만 4스텝 24.55초, 피크 18.34GB |
| CPU 연산 | BF16 및 BNNS BF16/FP32 출력 | 모델 잠재값 불일치, 4스텝 BNNS 17.19초로 기존 16.51초보다 느림 |
| CPU 행 분할 | FP32 BLAS 4행 타일 병렬 | 동일 출력, 전체 4스텝 16.95초 vs 앞뒤 17.09/17.21초. 차이가 작고 스레드 복잡성 증가 |
| 가중치와 투영 결합 | CPU/GPU 가중치 전치, 사전 포장 BNNS, GPU QKV+MLP 결합 | 동일 출력 사례에도 이득 불명 또는 느리고 추가 메모리 사용 |
| GPU 커널 | 수제 Metal GEMM 15개, GEMM 타일·swizzle, attention tile/head 분할, FP16 | 기존보다 빠르지 않거나 수치 불일치. 측정 형상과 MLX 버전에 한정 |
| 행렬 알고리즘 | Strassen 1/2단계 | 버퍼·합산 비용으로 느림 |
| 분기 실행 | 별도 CPU/GPU stream, 별도 branch 제출, 3개 출력 제출, 블록 격회 제출, graph compile | 기존 attention+MLP 두 출력 동시 제출보다 느리거나 개선 불명 |
| 활성화 결합 | CPU/GPU 투영에서 별도 활성화 또는 두 버퍼를 직접 읽는 Metal SiLU | 직접 읽기 4스텝 17.16초 vs 기존 17.29초, 비트 일치하나 단일 측정 차이가 작음 |
| 마지막 query 생략 | 마지막 블록 참조·텍스트 query 투영 생략, K/V 유지 | 4스텝 기준→시제품→기준 17.07→17.18→17.58초, 비트 일치. 개선 불명 |
| ANE/Core ML | 검증된 동일 BF16 경로 확보 못함 | 실사용 동등성과 성능 미검증 |
| 캐시·전력 상태 | 4스텝 동안 시스템 전체 swap in/out 증가 0; 전원 연결, 저전력 모드 꺼짐 | 이 실행만의 시스템 전체 관찰. 다른 실행의 메모리 지연은 배제 못함 |

## 다음 작업 시작점

1. **조건 고정과 반복 측정:** 같은 모델·토큰·16스텝·입력·시드로 번갈아 실행하고 디노이징과 전체 생성 시간을 분리한다. 온도·부하·첫 가중치 준비 포함 여부를 기록한다.
2. **출력과 화질 확인:** 잠재 텐서의 비트 비교와 실제 RGB 픽셀 비교를 분리한다. 계산을 근사하거나 입력·스텝을 바꾸면 인물·눈·로고·작은 글자를 여러 사진에서 직접 평가한다.
3. **프로파일링부터:** MLX lazy eval은 CPU/GPU 계산·스케줄링·동기화가 섞인다. 강제 동기화한 층별 시간은 전체 중첩 시간에 단순 합산하지 않는다. 하드웨어 트레이스나 입증 가능한 새로운 연산 경로를 확보한 뒤 후보를 선택한다.
4. **제외 후보의 재검토 조건:** 다른 MLX/OS, 하드웨어, 토큰 형상, 커널, 정밀도 또는 데이터에서 근거가 바뀌었을 때만 위 기록을 확인하고 재실험한다. 새 조건과 과거 결과를 함께 남긴다.
