# 16스텝 동일 출력 최적화 재측정

M3 Pro 36GB, MLX 0.32.4, FLUX.3 Klein Q8, 같은 512×352 편집 입력 safetensors(출력 704·참조 1320·텍스트 240 토큰), 시드 7. 모델 로딩·인코딩·디코딩·출력 저장 제외. 첫 가중치 준비는 포함. 시점과 부하가 달라 각 1회 값의 차이를 반복 가능한 개선으로 해석하면 안 된다.

| 경로 | 16스텝 디노이징 | Python 최종 잠재값 |
|---|---:|---|
| Python 최적화 재측정 | 76.65초 | 기준 |
| C++ CPU 30% 분배 | 76.18초 | 비트 일치 |
| C++ 고정 영점 timestep 임베딩 캐시 + schedule delta 일괄 계산 | 73.39초 | 비트 일치 |
| C++ 기존 경로 (직후) | 72.99초 | 이전 검증에서 Python과 비트 일치 |
| C++ residual 커널의 attention/MLP 입력 의존 순서 변경 | 73.82초 | 비트 일치 |

CPU 분배 변경은 연산의 출력 채널을 다른 장치에서 계산한다. 16스텝 동일 입력에서 비트 일치했지만 다른 입력과 플랫폼 전반의 동일성은 보장하지 않는다. 보조 계산 변경은 반복을 줄이지만 이번 연속 측정에서 속도 개선은 나타나지 않았다. 의존 순서 변경은 Metal 커널의 입력 선언 순서만 바꾸고 원래 연산식을 유지한다. 어느 후보도 기본 경로에 적용하지 않았다.

## 대기/그래프 계측

동일 편집 텐서, 4스텝 실험, 각 1회. Python은 최적화 경로, C++은 기존 경로. 첫 스텝에는 준비·컴파일 등이 섞여 다음은 2~4번째 스텝이다.

| 구간 | Python 2~4번째 스텝 | C++ 2~4번째 스텝 |
|---|---|---|
| forward 그래프 생성 호출 | 4.1~4.3ms | 0.6~0.8ms |
| 스케줄 처리 | 0.2~0.5ms | 약 0.2ms |
| 최종 eval 호출 | 4.50~4.72초 | 4.44~4.50초 |

MLX는 지연 실행하므로 eval에는 계산 그래프 처리·스케줄링·CPU/GPU 연산·동기화가 함께 들어간다. 이 계측만으로 GPU 점유율이나 Python이 담당하는 모든 비용을 확정할 수 없다. 다만 관찰된 그래프 생성 호출 차이는 스텝당 수 ms로 4초대의 전체 스텝에 비해 매우 작다. 첫 준비 단계나 전체 이미지 생성 시간은 이 범위에 포함되지 않는다.

## 마지막 이미지 토큰 및 분기 병렬 제출

마지막 joint block의 출력에서 실제로 사용하는 이미지 토큰만 query/MLP 계산하고, K/V는 모든 토큰을 유지한다. 직후 이어서 측정한 동일 16스텝 실행은 기존 72.81초, 변경 71.82초이며 최종 잠재값이 비트 일치했다. 텍스트 8스텝 및 최적화 비활성 편집 1스텝에서도 각각 기준과 비트 일치했다. 단일 샘플과 단일 머신 기록이다.

각 큰 블록에서 attention 출력과 MLP 입력을 `async_eval`로 함께 제출한다. 동일 편집 16스텝 64.62초, 실제 C++ 실행기로 재빌드한 후 64.60초이며 Python 기준과 잠재값이 비트 일치했다. 텍스트 8스텝은 17.01초로 기존 결과와 비트 일치했다. 기존 72.81초와 64.62초는 동일 입력이지만 중간에 다른 실험이 있어 엄격한 순차쌍이나 반복 통계는 아니다. 모델 로딩·인코딩·디코딩은 제외한다. 50초 목표는 미달이다.

추가 후보 중 4스텝 편집에서 기존 분기 제출 16.51초, 블록 하나씩 건너뛰며 제출 17.20초, 두 분기 별도 제출 27.22초, 최종 두 출력 제출 18.03초였다. CPU 분할 30%는 16.97초, 55%는 18.82초로 기본 45%보다 느렸다. 입력이 동일하고 각 1회이며 다른 환경에 일반화하지 않는다.

같은 사진의 시드 19에서도 실제 C++ 실행기 16스텝은 64.49초였고 해당 시드 기준과 잠재값이 비트 일치했다. CPU Q8 직접 행렬곱은 작은 512×3072×1024 실험조차 FP32 약 2.7ms에 비해 매우 느려 측정을 중단했다. attention 출력 및 MLP 출력에도 CPU 분할을 추가한 시제품은 4스텝 24.44초로 느려 적용하지 않았다.

실제 Python 인코딩/C++ 실행/VAE 디코딩 경로에서 동일 편집의 16스텝 디노이징은 65.92초였고 기존 생성 결과와 512×352 RGB 픽셀이 모두 일치했다. CPU matmul을 2개의 MLX CPU stream으로 분할한 시제품은 4스텝 23.97초로 느려 적용하지 않았다.

추가 4스텝 후보: GPU용 별도 stream 17.16초, CPU 2개 stream 23.97초, MLP의 CPU/GPU별 활성화 분리 17.52초, 각 스텝의 참조/텍스트 early block을 개별 그래프로 미리 계산 18.35초. 각각 1회이며 적용된 16.51초 시제품보다 느려 유지하지 않았다. early block 선계산과 MLP 활성화 분리는 해당 비교에서 잠재값이 비트 일치했다. CPU/GPU 채널 분할 40/42/47%는 각각 17.28/17.27/18.06초, 45%는 다른 시점에 16.51초였다. 단일 측정이며 시스템 상태 차이가 있어 작은 차이를 일반화하지 않는다.

M3 Pro에서 QKV 크기 2264×3072×9216의 BF16 matmul을 별도로 반복했을 때 MLX와 PyTorch MPS는 각각 약 31~34ms였고, 난수 단일 입력의 출력은 일치했다. 미시 행렬곱 실험이라 전체 모델 경로의 속도와 품질을 입증하지 않는다.

## CPU BNNS 미시 실험

M3 Pro의 독립 2264×3072×8256 행렬 실험에서 BNNS BF16 입력·FP32 출력은 72.7~73.7ms, FP32 cblas_sgemm은 83.6~89.0ms였다. 동일한 BF16 입력으로 결과를 BF16으로 반올림한 경우 18,691,584개 중 5,256개가 달랐다. 무작위 행렬 단독 시험이며 모델 속도나 화질 개선이 입증된 것은 아니다. 출력 일치가 보장되지 않아 적용하지 않았다. 해당 API는 현 SDK에서 deprecated다.

BNNS를 MLX CPU primitive 시제품으로 연결해 4스텝 편집을 추가 측정했다. BF16 입력과 FP32 출력의 BNNS 행렬곱 뒤 BF16 반올림을 적용한 경우 17.19초였고 기준 대비 잠재 RMSE 0.07631, 최대 차이 2.20959로 비트 불일치했다. BF16 출력은 17.16초, RMSE 0.07895였다. 두 경로 모두 기존 비동기 16.51초 단일 측정보다 느렸으며 동일 출력을 훼손하므로 적용하지 않았다. 해당 실험은 `bnns-model-fp32.cpp`, `bnns_primitive_fp32.h`에 남아 있다.

분기 결합 전에 attention·CPU 투영·GPU 투영을 세 출력으로 묶어 비동기 제출하는 시제품은 4스텝 18.08초였다. 기존 비동기 경로의 16.51초 단일 기록보다 느려 적용하지 않았다. 시제품은 `parallel-three-roots.cpp`이다.

## 동일 토큰 재사용 가능성

시드 7의 실제 16스텝에서 각 중간 잠재값을 저장하고 다음 스텝에서 모델에 입력되는 BF16 값으로 변환해 비교했다. 초기값→1스텝과 이후 모든 인접 쌍에서 이미지 토큰 704개 중 128개 성분이 전부 같은 토큰은 0개였다. 개별 성분의 일치율은 첫 쌍 9.49%, 마지막 쌍 0.32%였다. 이 표본에서는 입력이 완전히 같은 이미지 토큰만을 재사용하는 방법으로 계산을 줄일 수 없다. 쓰기 측정이 추가된 실행은 속도 비교에 사용하지 않으며, 최종 잠재값은 Python 기준과 비트 일치했다. 한 입력에 대한 관찰로 일반화하지 않는다.

격리한 MLX 0.32.4 실험 빌드에서 4개의 사전 빌드 Metal GEMM 타일(64×32×32, 64×64×16 with 1×2, 32×64×16, 32×32×16)을 큰 BF16 NT 행렬곱에 적용했다. 각각 4스텝 17.91·18.08·17.93·17.84초였고 기본 타일은 별도 단일 측정 17.41초였다. 네 결과 모두 비트 일치했지만 안정적 가속은 확인되지 않았다. 작업 순서를 바꾸는 swizzle 1·2·3·4는 각각 17.19·17.38·17.48·17.92초로, 모두 비트 일치했으나 기본 대비 1회 측정의 작은 차이에 불과했다. 설치된 MLX는 수정하지 않았다.

고정 가중치 BNNS fully-connected 필터는 4스텝 21.99초로 기준 16.51초보다 느렸으나 최종 잠재값은 비트 일치했다. CPU/gpu 가중치를 각각 미리 전치한 실험은 19.58초/18.44초, QKV와 MLP GPU 투영을 결합한 실험은 18.44초였으며 모두 4스텝 비트 일치했다. QKV에 CPU 60%를 배정하고 MLP를 전부 GPU에서 처리한 실험은 25.02초였다. 모든 시간은 별도 단일 실험이다.

## 토큰 축 장치 분할과 참조 특징 기록

MLP 입력 투영을 출력 채널이 아니라 이미지/참조 토큰 축으로 나누어 CPU 45%, GPU 55%에서 계산하고 토큰 축으로 결합한 시제품은 4스텝 24.55초, MLX 추적 피크 18.34GB였다. 기준 4스텝과 잠재값은 비트 일치했지만 기존 경로의 16.51초보다 느려 적용하지 않았다. 가중치 전체를 양쪽 장치 형식으로 보관했다.

시드 7 편집의 매 스텝에서 5개 참조 초기 블록의 최종 BF16 특징을 저장해 인접 스텝을 비교했다. 참조 토큰 1320개 중 3072개 성분이 전부 일치하는 토큰은 모든 인접 쌍에서 0개였고 성분별 일치율은 0.40~6.07%였다. 최종 잠재값은 Python 기준과 비트 일치했다. 파일 쓰기와 동기화가 추가됐으므로 이 실행을 속도 비교에 사용하지 않았다. 이 사진에서는 조건 특징의 완전 일치 토큰 재사용으로는 절감할 수 없으며, 다른 입력에 대한 일반적 결론은 아니다.

## CPU 타일 및 attention 커널 실험

FP32 cblas_sgemm의 2264×3072×8256 임의 입력을 CPU에서 네 개의 행 타일로 병렬 계산하면 단일 호출 84.13ms 대비 최선의 반복 73.64ms였고 BF16 출력이 일치했다. 이를 MLX CPU primitive로 4스텝 편집 모델에 연결하자 기존 17.09초 → 시제품 16.95초 → 기존 17.21초였다. 시제품 최종 잠재값은 비트 일치했으나 단일 교차 측정의 차이가 작고, 매 블록에서 스레드를 새로 생성하는 복잡성을 정당화할 만큼 개선이 크지 않아 적용하지 않았다.

분리된 MLX JIT 빌드에서 시퀀스 2264, 헤드 24, 차원 128의 임의 BF16 attention을 비교했다. 기준 key 타일 16은 중앙값 16.04ms, key 타일 32/64는 17.44/18.86ms였고 최대 BF16 차이 0.000488로 비트 불일치했다. query 타일 32 기준은 15.88ms, query 타일 64는 17.93ms로 출력 일치했으며 타일 96은 20.33ms이고 출력이 달랐다. 별도 실행의 query 타일 16/8은 각각 18.11/31.44ms이고 기준과 일치했다. 헤드 분할 2는 22.51ms로 기존 17.00ms보다 느리고 출력이 달랐다. 각 측정은 동일 입력으로 5회 실행의 중앙값이며, 전체 모델 벤치마크가 아니다. 새 커널은 설치된 MLX에 적용하지 않았다.

## 정확한 0 기반 생략과 메모리 관찰

시드 7 편집 입력의 16개 timestep에서 초기 블록 및 joint 블록의 image/condition/text modulation gate를 살펴봤다. 각 벡터의 BF16 3072개 값 가운데 정확히 0인 값은 모두 0개였다. 동일 입력의 첫 joint 블록 입력은 정확한 0이 0.07984%, CPU/GPU MLP 입력 가중치는 각각 0.04731%/0.04841%, SiLU 활성화 결과는 0%였다. 활성화와 가중치 관찰은 1스텝·1개 블록의 표본이다. 이 표본의 정확한 0만 생략해서는 목표에 필요한 큰 절감을 기대하기 어렵다. 프로브는 `gate-probe.cpp`, `sparsity-probe.cpp`다.

동일 4스텝 native 실행은 17.66초, MLX 추적 피크 12.42GB였다. 실행 전후 시스템 전체 `vm_stat`의 swapins/swapouts 증가는 각각 0이었고 pageins는 211 증가했다. 시스템 전체 누적 카운터를 비교한 관찰이므로 개별 프로세스의 모든 메모리 지연이나 다른 실행의 스왑 상황을 증명하지는 않는다. 로그는 `parity/memory-observe.log`에 있다.

## 마지막 블록의 query 투영 생략

마지막 joint 블록에서 참조·텍스트 토큰의 query를 계산하지 않고 이미지 토큰에 대해서만 query를 투영하는 시제품을 만들었다. Key/value는 모든 토큰을 유지하고 기존 융합 커널의 입력을 맞추기 위해 남은 query를 0으로 채웠다. 같은 편집 입력의 4스텝을 기존 경로 → 시제품 → 기존 경로 순으로 한 번씩 측정했을 때 각각 17.07초 → 17.18초 → 17.58초였고, 시제품은 첫 기준의 최종 잠재값과 비트 일치했다. 측정 변동 안에 있어 속도 개선을 입증하지 못했고 기본 구현에는 적용하지 않았다. 시제품은 `final-q-prune.cpp`, 각 로그는 `parity/control-a.log`, `parity/final-q-prune.log`, `parity/control-b.log`다.

## 분할 투영 결과의 직접 활성화

MLP 입력 투영의 CPU와 GPU 출력을 연결하는 중간 텐서를 만들지 않고, 두 출력 버퍼를 직접 읽어 기존과 같은 BF16 반올림을 거치는 SiLU 곱을 계산하는 Metal 시제품을 만들었다. 같은 편집 입력에서 4스텝 시제품 17.16초, 직후 기존 경로 17.29초였고, 시제품의 최종 잠재값은 별도 기존 실행과 비트 일치했다. MLX 추적 피크는 각각 12.44GB/12.42GB였다. 각 1회인 데다 차이가 기존 시간 변동 범위에 있어 개선을 입증하지 못했다. 기본 구현은 변경하지 않았다. `split-silu.cpp`, `parity/split-silu.log`, `parity/split-silu-control.log`에 실험을 남겼다.
