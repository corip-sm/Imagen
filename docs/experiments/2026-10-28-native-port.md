# C++ 지연 재분석

M3 Pro 36GB, MLX 0.32.4, 동일 Q8 checkpoint. 시드 7의 512×352 편집에서 미리 같은 safetensors로 저장한 이미지 704·참조 1320·텍스트 240 토큰을 두 실행기가 사용했다. 각 행은 1회이며 순차 실행했다. 디노이징에 가중치 준비를 포함하고 모델 로딩·인코딩·디코딩·저장은 제외한다. 원본 사진과 입력 텐서는 로컬 outputs에만 있다.

| 실행기 | 스텝 | 시간 | 최종 잠재값 |
|---|---:|---:|---|
| 기존 Python 최적화, 캐시 제한 1GB | 4 | 19.89초 | 기준 |
| C++ 융합 전 | 4 | 23.22초 | Python 기준과 동일 (기존 비교) |
| C++ 융합 이식 후 | 4 | 19.61초 | Python 기준과 비트 일치 |
| 기존 Python 최적화, 기본 캐시 제한 | 8 | 38.33초 | 기준 |
| C++ 융합 이식 후, 기본 캐시 제한 | 8 | 37.76초 | Python 기준과 비트 일치 |
| 기존 Python 최적화, 기본 캐시 제한 | 16 | 75.07초 | 기준 |
| C++ 융합 이식 후, 기본 캐시 제한 | 16 | 75.38초 | Python 기준과 비트 일치 |

4스텝 비교는 캐시 제한이 다르므로 해당 차이는 융합 커널 효과의 정확한 정량값이 아니다. 8/16은 입력과 캐시 기본값을 맞췄지만 반복 측정이 아니고 순서·온도·시스템 부하의 영향을 받는다. C++과 Python 둘 다 빠른 행렬곱은 MLX C++/Metal에서 실행된다. 이전 C++ 포팅은 Q/K 정규화·RoPE·V 배치, SwiGLU, modulation 및 residual 융합을 빠뜨렸다. 이를 복원했다. 8스텝에서 양쪽 정상 단계는 약 4.6초로 비슷해 Python 루프 제거만으로 큰 차이를 예상하기 어렵다.

같은 편집 입력에서 C++ CPU 출력 채널 비율 30/60/75%의 4스텝 단발 실험은 각각 18.80/23.35/28.25초였고 모두 비트 일치했다. 별도 시점의 45%는 19.61초였으나 순서·발열·캐시 효과 때문에 30%가 일관되게 우월하다고 결론 내릴 수 없다. 기본 45%는 그대로 유지한다.

CPU에서 스케줄 간격을 미리 산출해 매 스텝의 `dt.eval()`을 없앤 시제품은 8스텝 40.92초였고 최종값은 비트 일치했다. 실행 중 단계 시간이 4.6~6.1초로 변동해 기존 37.76초와 직접 비교하기 어렵다. 개선 근거가 없어 배포 경로에 적용하지 않았다.

융합 적용 후 준비 단계에서 원본 Q8 가중치 참조를 eval 전에 해제하는 변경을 추가했다. 동일 4스텝 입력에서 C++ MLX 피크는 14.40GB에서 12.39GB로 줄었고 최종 잠재값은 기존 Python과 비트 일치했다. 계산 시간은 각각 19.61초, 19.73초로 각 1회여서 속도 차이를 판정하지 않는다. C++ 프로세스만의 MLX 피크이며 Python 전처리·디코딩의 메모리는 포함하지 않는다.
