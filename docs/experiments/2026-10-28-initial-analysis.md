# Imagen 속도 심층 분석 — 2026-10-28

## 목적과 결론

M3 Pro / 통합 메모리 36 GB의 현재 FLUX.3 Image Klein Q8 경로를 대상으로 분석했다. 가장 큰 즉시 실험 후보는 8스텝이며, 정확히 동일한 결과가 필요한 경로에서는 실사용 크기·참조 토큰 수별로 행렬곱 분배를 다시 측정하는 것이 우선이다. 8스텝은 모델 호출을 절반으로 줄이지만 출력이 바뀌므로 품질 승인이 필요하다. 어느 기법도 모든 작업에서의 속도나 품질을 입증한 것은 아니다.

## 새로 측정한 것

MFLUX 0.24.0, MLX 0.32.4, 기존 Q8 모델, 시드 7, 동일한 영어 프롬프트 임베딩과 초기 잡음. 각 조건 1회, 별도 프로세스, MLX 캐시 제한 1 GB. 디노이징 전체에 첫 가중치 준비는 포함하고 모델 생성·로드, 텍스트 인코딩, VAE 디코드, 저장은 제외했다. 수치는 전체 CLI 시간이 아니다. `512-text/comparison.json`, `384-text/*.json`, `512-{8,4}step/optimized.json`에 원시 기록이 있다.

| 사례 | 시간 | MLX 피크 | 비교 |
|---|---:|---:|---|
| 512², 16스텝, 기본 MFLUX | 45.73초 | 6.24 GB | 기준 |
| 512², 16스텝, Imagen | 40.60초 | 11.55 GB | 11.2% 감소; 최종 FP32 잠재값 비트 일치 |
| 512², 8스텝, Imagen | 20.01초 | 11.55 GB | 16스텝 대비 50.7% 감소; 출력 달라짐 |
| 512², 4스텝, Imagen | 10.35초 | 11.55 GB | 16스텝 대비 74.5% 감소; 출력 달라짐 |
| 384², 8스텝, 기본 MFLUX | 13.58초 | 6.11 GB | 576 이미지 + 80 텍스트 토큰 |
| 384², 8스텝, 임시로 기준 512토큰 | 13.40초 | 11.22 GB | 1.3% 감소; 최종 FP32 잠재값 비트 일치 |

384 실험은 배포 코드를 바꾸지 않고 두 모듈의 `MIN_OPTIMIZED_TOKENS`를 별도 프로세스에서 512로 바꿨다. 8스텝에 가중치 준비 약 0.73초가 포함되며 한 번씩의 측정이어서 1.3% 차이는 노이즈일 수 있다. 16스텝, 직사각형 출력과 여러 참조 조합에도 적용된다는 뜻이 아니다. 기본 코드에서 384² 텍스트 전용의 총 656토큰은 1024 미만이므로 원본 경로다. 512²는 이미지 1024 + 텍스트 80이므로 image 및 joint 33개 블록이 최적화된다.

시각 비교: 16·8·4스텝 이미지 (로컬 outputs에 보관, 저장소에는 포함하지 않음). 한 장면에서 세 결과 모두 건물과 젖은 도로를 만들지만 구도와 디테일이 다르다. 인물 정체성, 작은 글자, 이미지 편집 또는 사용자 선호는 검증하지 않았다. 8·4스텝은 같은 초기 잡음과 임베딩을 사용하되 스케줄 자체를 다시 구성한 결과다. 숫자 동등성을 요구할 수 없다.

## 비용 구조

- 출력 토큰은 대략 `(너비 / 16) × (높이 / 16)`이다. 512²는 1024, 384²는 576, 384×512는 768이다. 각 참조 이미지도 준비된 픽셀 면적에 따라 토큰이 추가된다.
- 5개 early 블록은 image / image_cond / txt를 각각 처리하고, 28개 joint 블록은 합친 전체 토큰을 처리한다. joint 길이 L은 출력 + 모든 참조 + 텍스트 토큰이다.
- 폭 d=3072, MLP 비율 3인 joint 블록에서 대략적인 주요 행렬곱 MAC 수는 투영·MLP 약 `13 L d²`, attention 두 곱 약 `2 L² d`다. 연산 수 모델일 뿐 실측 지연이나 메모리 대역폭을 예측하지 않는다. 1000~3000 토큰에서 무조건 attention이 병목이라고 단정할 근거가 없다. 투영, 가중치 읽기, CPU/GPU 동기화, attention 및 전처리를 각자 측정해야 한다.
- 예를 들어 출력 1024, 텍스트 80, 참조 1024 토큰이면 joint 길이는 1104→2128이다. joint 투영 계산량은 약 1.93배, attention 항은 약 3.72배가 된다. 전체 속도 비율은 초기 블록, 메모리 및 다른 단계가 섞이므로 이 수치와 다르다. 별도의 참조 crop도 토큰을 추가한다.
- 현재는 Q8을 큰 블록에서 BF16으로 한 번 복원하고 MLP 입력의 출력 채널 약 45%를 CPU FP32에 맡긴다. 분배율, 1024 기준, 메모리 한계는 M3 Pro와 입력 크기에 의존한다. Q4/Q6은 현재 Q8 전용 준비 조건을 통과하지 못하므로 단순히 체크포인트만 바꾼다고 같은 경로의 가속이 유지되지 않는다.

## 우선순위와 실험 설계

1. **8/12/16스텝 품질 대 속도**: 동일 프롬프트·시드·참조로 인물 동일성, 눈, 글자, 사물 제거, 작은 상품, 여러 참조 각각 최소 5건 이상 비교하고 작업 성공률을 블라인드 평가한다. 4스텝도 공격적 모드로 비교한다. CLI의 `STEPS=8`은 이미 지원하지만 기본값 변경은 품질 확인 후 결정한다. 얼굴/문자 편집 실패율을 시간 절약과 함께 기록한다. 공식 기본은 16스텝이다.
2. **최적화 분기와 CPU 분배 재탐색**: 336×512, 384×512, 512² 텍스트 및 총 참조 토큰 0/512/1024/1536/2560 등을 기준으로 0/0.2/0.35/0.45/0.55/0.7 분배, 원본 Q8과 전체 GPU BF16을 비교한다. image·image_cond·joint를 따로 선택한다. 실사용 시간과 피크 메모리뿐 아니라 같은 입력 최종 잠재의 비트 동등성을 확인하고 A/B 순서 교차, 예열과 반복으로 중앙값·범위를 기록한다. 디코딩 이후 작업시간도 따로 잰다. 경쟁 앱·메모리 압박·발열을 통제한다.
3. **참조 토큰을 작업 의도에 맞춰 절약**: 현재의 중요한 영역 판별과 함께 자동 예산, 전체 참조 해상도, crop 해상도·개수를 비교한다. 이미지 의존성을 줄인 만큼 정보를 잃으므로 얼굴 및 글자 손실을 필수로 평가한다. 같은 출력 및 작업 조건에서 고해상도 참조를 기준으로 비교하고, 전처리와 전체 시간을 포함한다. 타일 세부를 큰 검은 padding 캔버스로 만드는 경우 유효 면적 비율을 조사한다.
4. **모델 상주와 반복 작업 재사용**: 현재 CLI는 매번 프로세스와 모델을 새로 띄우고 prompt_cache도 프로세스 안에서만 유지된다. 상주 프로세스에서 동일 프롬프트 인코딩, 동일 참조 VAE 결과, 위치 임베딩 및 복원 가중치를 재사용하면 두 번째 작업의 준비비를 줄일 가능성이 있다. 모델 수명 중 입력 크기 변경은 현재 최적화에서 검증하지 않았고, 조건·크기·dtype·가중치·LoRA를 캐시 키에 포함하고 무효화해야 한다. 동일 스케줄·참조·프롬프트의 여러 시드라면 각 target timestep별 독립적인 early text/reference 블록 결과를 요청 간 재사용하는 방안도 이론상 가능하다. 메모리 비용과 정확성·동시성 실측이 필요하다. 첫 작업은 빨라지지 않을 수 있다.
5. **변하지 않는 부분만 정확히 캐시**: RoPE는 ID가 고정인데 현재 매 스텝 NumPy float64에서 계산한다. 모델 입력 임베딩 중 고정 텍스트·참조 투영, 위치 ID 및 RoPE를 요청 단위로 캐시하는 프로토타입을 만들고 전체 지연을 잰다. 단, 동일한 수치 순서·dtype·참조 번호를 보존해야 한다. 모든 단계가 합쳐도 얼마나 줄어드는지는 아직 모른다.
6. **근사 캐싱 / 블록 생략**: 일정 스텝의 residual, attention 또는 일부 블록을 재사용해 계산량을 줄인다. FLUX.3 flow-map은 다음 target timestep을 text와 image_cond 변조에도 더하므로 early stream조차 서로 다른 스텝 간 그대로 재사용할 수 없다. joint 블록의 참조 표현도 생성 중인 이미지와 상호작용한다. 16스텝은 이미 증류된 짧은 스케줄이므로 캐시 오차가 커질 수 있다. 8/12/16스텝에서 초반/후반을 보존하는 선택적 스킵을 비교하고, 속도와 주관적 실패율을 함께 측정한다. TeaCache/AutoTarget의 다른 모델 속도 수치를 그대로 적용하지 않는다.
7. **정밀도와 모델 변경**: Q6/Q4, 혼합 비트, FP16 연산, 다른 증류 모델 또는 4~8스텝 전용 재학습·LoRA를 독립적인 품질 실험으로 취급한다. Q8→Q4 재양자화의 손실과 원본 BF16→Q4의 손실을 구분하고, 텍스트 인코더와 transformer를 별도로 바꾼다. 기존 실험에서 FP16은 수치 차이가 났고 유의미한 추가 이득이 없었다. 다른 체크포인트의 라이선스, 모델 접근성, 이미지 편집 지원과 설치 비용도 확인한다.
8. **전문적인 프로파일링**: 전체 작업을 입력 준비/Vision, 로딩, 텍스트 인코딩, 참조 VAE, 첫 스텝 준비, 이후 스텝, VAE 디코드/저장으로 구분한다. Xcode Instruments의 Metal System Trace와 CPU 샘플링으로 GPU 유휴, 커맨드 제출, 동기화, 메모리 압박, 실제 행렬곱 및 attention을 확인한다. 강제 `mx.eval`을 각 블록에 삽입한 시간은 비동기/병렬 실행을 깨므로 전체 구성 시간으로 더하지 않는다. 그래프 `mx.compile`은 현 소스의 host float64 RoPE 때문에 그대로 추적할 수 없으므로 고정 RoPE를 분리한 뒤 소규모로 평가한다.

## 조심할 지름길

- 스텝 수 절반은 transformer 호출을 절반으로 줄일 뿐 전체 파일 저장 시간이 정확히 절반이라는 뜻이 아니다. 첫 작업 비용은 남는다.
- FLUX.2 KV 전용 모델의 reference cache 가속은 해당 모델에 맞춘 구조·가중치의 결과다. FLUX.3에 정확히 적용할 수 있다는 증거가 아니다.
- `MLX_METAL_FAST_SYNCH=1`은 CPU/GPU 동기화 비용을 줄일 가능성이 있으나 MLX 문서는 GPU가 멈출 수 있어 기본적으로 사용하지 말라고 명시한다. 이 Mac에서 실행하지 않았다.
- 기존 수제 Metal GEMM 15개, Strassen, FP16 및 다른 CPU 분배 실험에서 실패한 결과는 `docs/optimization.md` 참조. 입력 형태나 라이브러리 버전이 바뀌었다면 다시 측정할 수 있지만 이전에 실패했다는 사실을 빼지 않는다.
- 하드웨어 교체, 원격 GPU, 여러 Mac 병렬화는 별도 비용·전송·프라이버시 조건을 가진 옵션이다. 단일 이미지의 지연이 반드시 개선되는 것은 아니며 배치 처리량과 구분한다.
