# 개발과 검증

이전 저장소 정리 후 12개 모델 없는 회귀 검사를 통과했다. 과거 Python 런타임 제거 후에는 관련 해시 검사를 제외한 11개 검사를 통과했다. 숫자 진단 도구도 64×64·1스텝의 별도 baseline/optimized 프로세스로 실행해 최종 텐서 비트 일치를 확인했다. 이 작은 실행은 도구 연결 확인이며 가속 수치로 해석하지 않는다. 이미지 디코딩·생성은 하지 않았다.

## Python 환경

MFLUX는 `uv tool` 환경에 설치된다. 시스템 `python3` 대신 다음 실행기를 사용하면 모델 런타임과 같은 Python·Pillow·MLX 환경을 쓴다.

```sh
./scripts/python.sh -m unittest discover -s tests -v
```

테스트는 모델을 로드하거나 이미지를 생성하지 않는다. 임시 합성 입력과 검증용 CLI 호출을 사용한다. CI는 Linux·Python 3.12·Pillow로 같은 검사를 실행한다.

## 검사 범위

- 입력·출력 512 상한과 작은 출력 요청
- 비율 유지, 작은 입력 픽셀 보존, 방향 정보
- 원본에서 crop한 뒤 축소하는 순서
- 원본 파일 불변, 잘못된 영역·참조 개수 거부
- 자동 선택의 겹침 제거·추가 토큰 예산·여러 입력 번호
- 전체 분석기 실패 시 중단
- 편집 지시 보존, 참조 설명, 런타임 on/off의 CLI 전달
- README와 문서의 로컬 링크

과거 macOS 네이티브 검증에서는 실제 Vision으로 인물·합성 제품·영문/한국어 글자·빈 이미지·방향 정보·다중 입력을 확인했다. 공개 CI의 mock 검사는 실제 검출 정확도를 재평가하지 않는다.

직접 네이티브 전처리를 확인하려면 자신의 사진에 다음을 실행한다. 생성 모델은 실행하지 않는다.

```sh
./scripts/python.sh src/imagen/references/prepare_references.py \
  /path/to/photo.png --output-dir outputs/reference-check
```

## 수치 런타임 진단

과거 Python 진단 도구는 Git 커밋 `15b8bf1`에 보관되어 있다. C++ 실험의 조건과 결과는 [최적화 실험 정리](optimization-experiments.md)를 따른다.

## 그래프와 데이터

`benchmarks/data/`는 과거 숫자 증거다. 결과를 보기 좋게 만들기 위해 숫자나 측정 구간을 바꾸지 않는다. 입력 전략이 바뀐 실험은 동일 입력의 런타임 가속과 분리한다. SVG는 `scripts/render_benchmarks.py`로 재생성한다. 생성 SVG를 직접 편집하지 않는다.

## 로컬 경로 이전

이 작업공간에서는 기존 프로젝트 경로가 새 `Imagen/` 디렉터리를 가리키도록 호환 링크를 남겼다. 이전 실험 도구와 이미지 링크를 위한 `runtime_optimization`·`reference_optimization` 등의 로컬 별칭은 Git에서 제외한다. 배포 구조에는 `src/imagen/`의 한 벌만 유지한다. 과거 사용자 이미지·로컬 원시 기록은 ignored `outputs/`에 보존한다.

## 코드 변경

실행기 연산을 바꾸면 수치·시간·메모리를 함께 확인한다. source hash가 달라지면 과거 bitwise 결과를 새 구현의 보증으로 사용하지 않는다. 참조 선택은 화질에 영향을 줄 수 있으므로 입력 픽셀 검증과 최종 결과의 사용자 평가를 구분한다. [기여 안내](../CONTRIBUTING.md)를 참고한다.

## C++ 디노이저

`./setup.sh`는 설치된 MLX의 C++ 헤더·라이브러리로 `.cache/imagen-native/imagen-native`를 빌드한다. 실행기를 다시 빌드하려면 `./scripts/build-native.sh`를 실행한다. 디노이징의 트랜스포머·스케줄러는 C++이며, 프롬프트/참조 인코딩과 VAE 디코딩은 MFLUX Python이다. 텐서는 임시 safetensors로 전달하고 작업 후 임시 디렉터리를 제거한다.

M3 Pro / MLX 0.32.4에서 동일한 편집 입력의 8스텝 디노이징은 기존 Python 최적화 38.33초, 융합 커널 이식 후 C++ 37.76초였고, 16스텝은 각각 75.07초와 75.38초였다. 각 1회이며 모델 로딩·인코딩·디코딩은 제외한다. 두 경우 최종 FP32 잠재값이 비트 일치했다. 텍스트 512² 8스텝과 편집 4스텝도 비트 일치했다. 준비 단계의 원본 가중치 참조를 조기에 해제한 후 같은 편집의 4스텝 C++ MLX 추적 피크는 14.40GB에서 12.39GB로 낮아졌고 결과가 비트 일치했다. 이 수치는 C++ 프로세스만 포함한다. 다른 Mac, 여러 크기·시드, 메모리 압박 및 장시간 실행은 미검증이다.

C++ 경로는 큰 스트림에서 가중치 복원, Q/K/V 결합, CPU/GPU 분할과 Metal 융합 커널을 사용하며, 요청 내 고정 투영 및 위치 임베딩을 재사용한다. C++ 전환 자체가 더 빠르거나 스텝 수를 줄인다는 뜻은 아니다.

### 마지막 블록과 병렬 실행

마지막 joint 블록은 이미지 토큰만 출력에 사용하므로 전체 스트림의 K/V를 유지하면서 이미지 토큰의 query와 MLP 출력만 계산한다. 큰 블록에서는 독립적인 attention 출력과 MLP 입력을 함께 비동기 제출하여 CPU/GPU 실행이 겹칠 기회를 준다. 동일 편집 입력의 16스텝 단일 측정은 기존 C++ 72.81초, 새 경로 64.62초였고 잠재값은 Python 기준과 비트 일치했다. 두 수치는 연속된 실행이 아니며 모델 로딩·인코딩·디코딩은 제외한다. 편집 4스텝, 다른 시드의 편집 16스텝(64.49초), 텍스트 8스텝도 각각 해당 기준과 비트 일치했다. 비최적화 Q8 경로의 마지막 토큰 최적화도 편집 1스텝에서 비트 일치했다. 실제 이미지 생성 경로에서는 디노이징이 65.92초였으며 기존 생성 이미지와 RGB 픽셀이 모두 일치했다. 다른 크기와 하드웨어에서 비트 일치나 가속을 일반화할 수 없다.

### 고정 크기 그래프 재사용

고정 크기 그래프 컴파일은 실제 생성 경로에서 안정적인 가속이 확인되지 않아 기본 실행에 적용하지 않았다. 같은 512×352 편집 입력에서 16스텝을 두 번씩 측정했을 때 기존 C++ 75.38·73.48초, 그래프 재사용 71.87·71.73초였고 최종 잠재값은 매번 비트 일치했다. 별도 512² 텍스트 전용 실험에서는 36.74초와 36.94초로 개선을 확인하지 못했다. 모두 모델 로딩·인코딩·디코딩을 제외한 단일 머신 기록이며 모든 입력의 가속이나 동등성을 보장하지 않는다.

동일 편집의 실제 생성 경로 측정에서는 그래프 컴파일 75.91초, 직접 실행 74.28초였다. 각 1회이며 시간 차이의 재현성은 확인되지 않았다. 두 결과의 출력 픽셀은 일치했다. 블록 단위 그래프 재사용은 4스텝 19.06초로 최종 잠재값이 비트 일치했으나 뚜렷한 가속이 없어 적용하지 않았다.
